# 태스크 나누기

`../pm/SKILL.md`를 이 세션에서 읽지 않았다면 먼저 읽는다. 생성 규칙은 거기 "태스크 만들기"를 따른다.
작업 범위(조직·프로젝트)를 먼저 정하고 그 범위의 태스크만 다룬다(`../pm/SKILL.md` "작업 범위").

대상: $ARGUMENTS (비어 있으면 대화 내용에서 나눌 일을 찾는다.)

## 흐름

1. **대상 읽기**: `TASK-N`이면 `GET /api/tasks/N`과 `/github`, `/decisions`. 설명이면 그 내용과 대화.
2. **분할안**: 각 조각은 혼자 끝낼 수 있고, 확인 가능한 완료 조건이 있고, 대체로 PR 하나 크기다.
   조각마다 제목, 완료 조건, 다음 행동, 선행 조각, 담당자·기한 후보(대화에 근거가 있을 때만)를 정한다.
   두세 조각이면 충분한 일을 억지로 잘게 나누지 않는다.
3. **표로 확인**:

   | # | 제목 | 완료 조건 | 선행 | 담당 | 기한 | 이슈 |
   |---|---|---|---|---|---|---|

   같은 질문에서 이슈 생성 여부(전부 / 없음 / 골라서 — 저장소가 연결됐을 때만)와,
   원래 태스크가 있으면 그것을 어떻게 할지(상위로 두고 체크리스트를 조각 목록으로 바꾼다 / 그대로 둔다)를 묻는다.
   수정·제외 요청을 받으면 표를 고쳐 다시 한 번만 확인받는다.
4. **생성**: 순서대로 `POST /api/tasks`. 건마다 `--key split-<원래 id 또는 날짜>-<순번>`.
   `description` 첫 줄에 `상위: TASK-N`(원래 태스크가 있을 때)과 `선행: TASK-M`을 적는다.
   이슈를 고른 건은 `POST /api/tasks/{id}/github/issue`.
5. **원래 태스크 정리**: 고른 대로 `PATCH`(최신 `version`)로 체크리스트를 `[{"text": "TASK-M 제목", "is_done": false}]` 목록으로 바꾼다.
   원래 태스크를 취소하거나 지우지 않는다. 필요하면 사용자에게 맡긴다.
6. **보고**: 만든 `TASK-N` 목록과 이슈 링크, 실패한 건이 있으면 그 건과 이유.
