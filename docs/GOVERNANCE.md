# 개발 거버넌스 — 지금 있는 것과 앞으로

## 지금 (v1)

거버넌스는 **조직당 마크다운 한 덩어리**다. 서버는 저장·제공만 하고 내용을 검증하지 않는다.

| 층 | 무엇 | 어디 |
|---|---|---|
| 기본안 | 이상적인 제안. 조직이 고치지 않으면 이게 쓰인다 | `core/orgs/governance.py: DEFAULT_GOVERNANCE` |
| 조직 규칙 | 기본안을 덮어쓴 조직의 글. 비우면 기본안으로 복귀 | `Organization.governance` |
| 화면 | 조직 → 거버넌스. 멤버는 읽기, 관리자는 편집 | `/orgs/<id>/governance` |
| API | `GET·PUT /api/orgs/<id>/governance` | `core/api/routers/orgs.py` |
| AI | `get_governance(org_id)`. 서버 INSTRUCTIONS가 "쓰기 전에 먼저 읽어라"고 지시 | `mcp_server/.../server.py` |
| 사용법 | 도구 호출 순서·주의점. 규칙과 분리 | `skills/sandol-pm/SKILL.md` |

**왜 검증하지 않는가.** 기계가 막아야 하는 최소 규칙은 이미 `Task` 모델의 제약 조건에 있다
(기한 없는 `doing` 금지, `blocked` 사유 필수, 중요도 1~10, 완료 시각 필수). 그 위의 합의는
조직마다 다르고 자주 바뀐다. 코드로 굳히면 조직이 고칠 수 없고 배포가 필요해진다. 글로 두면
조직이 화면에서 바꾸고 AI가 다음 호출에서 바로 따른다. 대신 AI의 모든 쓰기는 `ChangeLog`에
`source="mcp"`와 토큰까지 남으므로 사후 확인은 가능하다.

## 앞으로

### 1. 승인 대기 큐 (하고 싶은 것, 아직 없음)

AI의 쓰기를 곧바로 반영하지 않고 `pending`으로 쌓아 관리자가 승인하면 반영하는 경로.

- `PendingChange(org, actor, token, target_type, target_id, payload, status, reviewed_by, reviewed_at)`
- 어떤 작업을 큐에 보낼지는 **조직이 고른다** — GitHub의 브랜치 보호 규칙처럼.
  예: "담당자 변경·기한 변경·done 처리만 승인 필요", "중요도 8 이상만", "전부 자유".
- MCP 쪽 변화는 작다. 쓰기 도구가 `{"status": "pending", "id": ...}`를 돌려받으면
  AI는 "승인 요청을 올렸다"고 말한다. 도구 목록은 그대로다.
- 화면: 조직 → 승인 대기. 승인·반려(사유)·일괄 승인.
- 이걸 만들 때 거버넌스 문서의 "사람에게 확인받고 하는 것" 절은 기계 규칙으로 옮겨 간다.
  문서는 남기고, 기계가 막는 항목에는 "이 항목은 설정에서 강제됩니다" 표시를 붙인다.

### 2. 설정 자유도 (승인 큐와 같은 뿌리) — 기획 완료, [IMPL-PLAN-4.md](IMPL-PLAN-4.md)

지금 기본값으로 굳어 있는 숫자·정책을 조직 설정으로 꺼낸다. 기본값은 그대로 두고 조정만 허용한다.

| 값 | 지금 | 설정으로 |
|---|---|---|
| 기본 기한 | 없음(사람이 입력) | 착수 시 +N영업일 자동 제안 |
| 동시 진행 한도 | 문서에만 "2개" | 초과 시 경고 또는 차단 |
| `review` 건너뛰기 | 자유 | 프로젝트별 강제 여부 |
| `blocked` 에스컬레이션 | 문서에만 "2영업일" | N일 지나면 Discord 알림 |
| AI 중요도 상한 | 문서에만 "7" | 실제 상한값 |

`OrgSettings` 한 테이블(JSONField 한 칸)로 시작하고, 화면은 항목이 늘어날 때 나눈다.
설정이 생기면 거버넌스 문서는 **설명**, 설정은 **강제**로 역할이 갈린다. 둘은 같은 화면에서 본다.

### 3. 프로젝트별 거버넌스 덮어쓰기

조직 규칙 위에 프로젝트가 한 문단을 덧붙이는 것. 요청이 실제로 나오면 만든다.
`Project.governance_extra` 한 필드와 `get_governance(project_id=...)` 정도면 된다.
