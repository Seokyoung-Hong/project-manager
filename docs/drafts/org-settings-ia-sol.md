# 조직 설정 IA 제안 — Sol 독립안

작성일: 2026-10-14. 공통 지시서의 요구 1~5를 반영했다. Claude 안은 열람하지 않았다. 이 문서는 분류·동작 제안이며 코드와 데이터는 변경하지 않는다.

## 1. 결론과 현재 구조의 차이

조직 메뉴의 **설정**을 모든 구성원에게 열고 기본 탭을 **내 정보**로 한다. 관리자는 같은 설정 안에서 **구성원 관리**를 열어 구성원별 정보를 고친다. 정책은 일하는 방법별 탭으로 나누고 GitHub·Discord 관리, 전사 서버 설정도 설정 안으로 옮긴다. 팀 작업·전사 작업·이슈 조회는 조직의 업무 메뉴에 남긴다.

현재 메뉴는 설정을 관리자에게만 노출하지만 설정 뷰 자체에는 일반 구성원 읽기 전용 분기가 있다. 따라서 ‘관리자만 접근 가능’과 ‘메뉴에서 관리자에게만 보임’을 구분해야 한다. **실명은 계정 공통 값이며 조직 표시 이름과 추가 정보만 멤버십 값이다.** 정정된 추가 요구 5에 따라 관리자는 실명을 읽기만 하고 조직 표시 이름·추가 정보 값만 수정한다. 조직용 실명 모델을 새로 만들지 않는다. [근거: core/web/templates/orgs/_tabs.html:15~17; core/web/views/orgs.py:593~629; core/accounts/models.py:14~17; core/orgs/models.py:77~80]

### 탭과 섹션 순서

| 순서 / 탭 | 노출·권한 | 섹션 순서 |
|---|---|---|
| 1. 내 정보 | 모든 구성원, 본인 정보 편집 | 이 조직에서 보이는 이름 → 내 실명(계정 공통)·조직 표시 이름 → 조직이 요청한 정보 → 관리자가 수정한 내 정보 이력 → 적용 규칙 안내 |
| 2. 구성원 관리 | 관리자 | 구성원 목록·구성원별 편집 → 초대·가입 전 구성원 → 구성원 관리 옵션(참여·업무 배정 / 이름 표시 / 요청할 정보 항목) |
| 3. 업무 규칙 | 관리자 편집, 구성원은 적용값 읽기 | 태스크 생성·기한 → 상태·검토 → 변경 사유 → 프로젝트 권한 → 프로젝트 기본값 |
| 4. 알림 | 관리자 | 기한 알림 → 막힘·검토 알림 → 주간 보고 → 채널 게시·GitHub 알림 |
| 5. 회의·전사 | 관리자 | 녹음 운영 → 공개·보관 → 전사 용어 → 전사 이용 정책 → 전사 수단·연결 점검 |
| 6. AI·자동화 | 관리자 | AI 자동완성 사용·이용 권한 → 조직 AI 연결·한도 → 외부 AI 쓰기 권한 → 태스크 작업 권한 → 조직·요청 관리 권한 |
| 7. 연동 | 관리자 | Discord 서버·알림 채널 → Discord 팀·프로젝트 채널 접근 → GitHub 앱·권한 점검 → 저장소 연결 현황 |
| 8. 조직 관리 | 관리자 | 저장 공간 → 설정 변경 이력 → 위험 구역 |

관리자는 탭 목록 전체를 보고 일반 구성원은 ‘내 정보 / 업무 규칙’만 본다. 업무 규칙 읽기 화면에는 구성원 관리·알림·회의 정책 중 **본인 업무에 적용되는 공개 가능 규칙**을 요약하여 함께 보여 준다. 편집 원본은 매핑표의 위치 하나뿐이다. 실명·추가 정보 값, 다른 구성원 상세 정보, 서버 주소·키·관리 이력은 이 요약에 넣지 않는다. 설정의 기본값·프로젝트 변경 허용·잠금은 위치만 옮기며 의미는 유지한다. [현재 잠금 설명: core/web/templates/orgs/settings.html:5~6]

## 2. 전체 매핑표

### 2.1 설정 정의 84개

목록의 기준은 `docs/drafts/settings-inventory.json`의 각 `key` 객체다. 77개는 조직 범위, 7개는 개인 범위다. 개인 범위 항목은 현재도 조직 설정에 나타나지 않으므로 ‘내 설정 그룹’이라는 이름만 보고 조직 안으로 옮기지 않는다. 전사 수단 7개는 현재 전사 메뉴에 있고, 숨김 1개는 현재 화면에 나오지 않는다. [근거: core/orgs/settings.py:1075~1103; core/web/views/orgs.py:598]

## 3. 구성원 관리 그룹에 모으는 것

이 그룹은 **사람을 조직에 넣고, 참여 방식을 정하고, 조직용 정보를 관리하는 작업**이다.

- 구성원 목록과 조직 역할, 제거, 가입 전 구성원, 조직 초대·개인 초대. `org.invite_days`, `org.invite_max_uses`는 초대 폼 바로 아래 옵션에 둔다. 개인 초대는 현재 1회용·7일 안내가 있으므로 일반 초대의 기본 만료·사용 횟수 정책과 같다고 표현하지 않는다. [teams.html:67,70~98]
- `org.tags_by`, `org.team_join_self`와 `task.doing_limit`, `task.doing_limit_mode`는 참여·업무 배정 옵션이다. 한도는 ‘구성원 한 명이 동시에 진행할 수 있는 태스크’이므로 사람별 운영 규칙과 함께 둔다. 업무 규칙 읽기 화면에서도 현재 적용 한도를 보여 준다. [인벤토리 해당 key]
- 이름 표시 옵션과 요청할 정보 항목은 각각 독립 제목·도움말을 둔다. ‘실명 표시 및 구성원 정보 저장’ 같은 결합 제목은 없앤다. 항목 설정은 **질문을 만드는 곳**, 구성원 편집은 **응답 값을 고치는 곳**이라는 차이를 먼저 설명한다.
- 프로젝트 생성·상태·설정 권한은 업무 규칙 / 프로젝트 권한에, `ai.manage_teams`와 조직 AI·전사 이용 권한은 각각 해당 기능 탭에 둔다. 사람에 관한 권한이라는 이유만으로 모든 기능 정책을 이 그룹에 넣으면 다시 거대 섹션이 된다.

### 구성원별로 열고 고치는 흐름

1. 목록 행에 표시 이름, 역할, 팀, 가입 상태, 필수 정보 완료 여부, ‘정보 수정’을 둔다. 클릭하면 같은 구성원 관리 탭의 우측 패널(모바일 시트)을 연다. 목록·스크롤은 유지한다.
2. 패널 상단의 ‘계정 정보(읽기 전용)’에는 **실명**을 보여 준다. ‘조직용 정보’ 아래 **이 조직 표시 이름 / 추가 항목 값 / 기술 태그** 순서로 편집한다. 실제 표시 이름 미리보기와 적용 조직 이름을 상단에 둔다. 실명·로그인 아이디·계정 표시 이름·다른 조직 정보는 편집 입력을 만들지 않는다.
3. 관리자는 모든 추가 항목 값을 기존 형식·길이·선택지 검증에 맞춰 수정할 수 있다. 실명 표시가 꺼져 있을 때만 조직 표시 이름 편집이 가능하다. 마지막 관리자 역할 변경·제거 제한은 유지한다.
4. 정보 저장은 한 구성원의 조직 한정 값만 원자적으로 반영한다. 역할 변경·제거·초대 발급은 목적이 다른 별도 동작으로 둔다. 값 변경이 없으면 이력·통지는 만들지 않는다. 폼을 연 사이 다른 사람이 고쳤으면 덮어쓰기 전에 최신값을 보여 주고 재확인하게 한다.
5. 저장 후 같은 패널에 완료 안내와 수정된 미리보기를 보여 준다. 목록의 이름·필수 완료 배지도 갱신한다. 관리자 수정으로 필수 값이 채워지면 해당 구성원의 조직 관문도 해제된다.

### 변경 이력과 본인 알림 — 권장 결정

**관리자 대리 수정은 이력·본인 통지를 필수로 한다.** 관리자가 통지를 끄는 옵션은 만들지 않는다. 이력에는 조직·대상 멤버십·수정자·시각·변경한 항목 이름·수정 경로를 남긴다. 변경 사유는 선택 입력으로 받되 값의 형식·선택지가 바뀌어 재입력이 필요할 때는 설명을 받는다. 이 안에서는 개인정보 이전 값·새 값을 공용 ChangeLog 문자열에 저장하지 않고, 값 이력 대신 ‘누가 무엇을 수정했는지’를 추적한다. 정책 변경 이력과 구성원 값 변경 이력은 화면에서도 구별한다.

본인은 내 정보의 변경 이력에서 자신의 수정 사실을 확인한다. 관리자에게는 해당 구성원의 이력만 제공한다. 별도 개인정보 통지 전달 기록을 남겨 알림 실패가 수정 실패로 보이지 않게 한다. 즉시 통지는 기존 전달 가능한 채널에 ‘관리자가 ○○ 조직의 내 정보를 수정했습니다’와 내 정보 링크만 보내고 실명·응답 값은 넣지 않는다. DM 수신 설정·미연결 때문에 즉시 전송하지 못해도 내 정보에 확인 전 안내를 유지한다. 신규 알림 저장·전달 수단의 존재는 아직 확인하지 않았으므로 **구현 조사 및 추가 범위**다. 가입 전 구성원은 수신 주체가 없으므로 통지 대기 상태로 두고 인계·가입 후 내 정보에서 확인하게 한다. 관리자의 조직 역할 변경·제거 통지와 개인정보 값 수정 통지는 별도 종류로 분리한다. 본인 실명 변경은 조직의 대리 수정 이력에 포함하지 않고 기존 계정 실명 변경 정책을 유지한다. [실명 값 이력 없음 결정: docs/IMPL-PLAN-13-realname-org-nickname.md:343]

## 4. 내 정보와 계정 공통 실명

### 값의 범위 — 정정된 추가 요구 5 적용

현재 `User.real_name`은 계정 공통 값이고 `OrgMembership.real_name`은 이전 데이터의 되돌리기용 열이다. 이 구조를 유지한다. 내 정보에서는 본인이 실명을 편집할 수 있지만 라벨을 **‘실명(계정 공통)’**으로 하고 ‘변경하면 계정 프로필과 실명으로 표시하는 모든 조직에 반영됩니다. 조직 관리자는 실명을 수정할 수 없습니다.’를 입력 아래에 표시한다. 조직별 실명으로 오해하게 하는 문구는 쓰지 않는다. [core/accounts/models.py:15~17; core/orgs/models.py:78~80; docs/IMPL-PLAN-13-realname-org-nickname.md:318]

실명 저장은 기존 계정 실명 검증·이름 캐시 무효화 규칙을 재사용하고 변경 대상은 항상 로그인한 본인이다. 관리자 구성원 편집에는 실명 수정 엔드포인트를 제공하지 않는다. 일반 계정 표시 이름은 읽기 전용 기준값으로만 보여 주며 계정 표시 이름·로그인·비밀번호 변경은 계정 설정에 남긴다. 실명은 현재도 조직 이름 계산에 직접 쓰이므로 새로운 데이터 이전 없이 본인 변경 결과를 모든 해당 조직에 반영한다. [core/accounts/services.py:31~50; core/orgs/names.py:34~42,70~74]

### 보이는 칸과 동작

| 상태 | 실명(계정 공통) | 이 조직 표시 이름 | 추가 정보 / 미리보기 |
|---|---|---|---|
| 실명 표시 끔 | 본인 편집 가능 / 관리자 읽기 전용. 일반 구성원에게 타인의 실명 미제공 | 본인·관리자 편집 가능. 비우면 계정 표시 이름 사용 | 정의된 순서로 입력. 미리보기는 조직 표시 이름 → 계정 표시 이름 |
| 실명 표시 켬 | 본인 편집 가능 / 관리자 읽기 전용, 조직 내 구성원 이름으로 표시 | **입력·빈 라벨·숨은 수정 필드 모두 없음**. 저장된 값은 보존 | 미리보기는 계정 실명. ‘이 조직에서는 실명이 표시됩니다’ 설명 |
| 실명 미입력 | 본인만 필수 입력, 계정 공통 관문 안내 | 표시 정책대로 | 관리자 대리 입력 불가. 가입 전 구성원은 인계·가입 때 본인이 입력 |
| 추가 필수 정보 미완료 | 표시 정책과 독립 | 표시 정책대로 | 부족한 항목을 앞에서 안내. 다른 조직은 영향 없음 |

실명 표시를 켤 때 관리자는 공개 효과와 표시 이름 편집 불가를 확인한다. 실명이 비어 있는 구성원은 본인이 입력해야 한다고 안내한다. 껐다 켜도 저장된 조직 표시 이름을 지우지 않으며 끄면 다시 적용한다. 서버도 켬 상태에서 표시 이름 변경 요청을 거부한다. 관리자의 표시 이름 편집 권한은 **실명 표시 끔 상태에 적용**한다. 켬 상태에서 숨긴 값을 우회 편집하는 예외는 요구 3과 맞지 않으므로 만들지 않는다. 관리자에게 실명 변경을 요청하는 대신 해당 구성원에게 본인 내 정보에서 수정하도록 안내한다.

### 저장과 필수 관문

내 정보에는 ‘내 정보 저장’ 주 버튼 하나를 둔다. 본인의 계정 실명·조건부 조직 표시 이름·추가 항목 값을 함께 검증하고 한 트랜잭션으로 저장한다. 실명이 바뀌면 제출 시 공통 범위에 영향을 준다는 요약을 명시한다. 하나라도 오류가 있으면 입력값을 유지하고 해당 칸에 오류를 붙인다. 본인 내 정보 저장은 본인 계정 실명만 갱신하고 임의의 계정 정보 수정 요청을 받지 않는다. 관리자 구성원 저장과는 입력 허용 목록·서비스 경로를 분리한다. [현재 분리: orgs/member_info.py:139~158; web/views/orgs.py:703~716]

저장 성공 후 탭·열린 섹션·스크롤을 유지한다. 정상 편집은 개요나 별도 페이지로 이동하지 않는다. 관문에서 들어온 사람에게는 저장 뒤 ‘입력이 완료됐습니다’와 ‘원래 하려던 일로 돌아가기’를 제공한다. 원래 주소는 현재 조직의 안전한 내부 GET 주소만 허용하고 POST 작업을 자동 재실행하지 않는다.

현재 관문은 계정 실명 미입력을 **조직 정보 미입력보다 먼저** 검사하고 프로필로 보낸다. 새 내 정보와 본인 저장 엔드포인트를 계정 실명 관문의 제한적 예외로 넣어 같은 탭에서 실명·필수 항목을 입력하게 한다. 예외는 `tab=me`에만 적용하고, 계정 실명 미입력자가 관리자 탭·일반 업무 데이터로 우회하지 않게 서버에서 분기한다. 계정 실명 요구는 실명 표시 켬·끔과 무관하게 유지한다. 추가 항목 미입력은 해당 조직만 차단한다. 관리자에게는 **계정 실명이 채워졌지만 자신의 조직 추가 정보가 미완료인 경우** 항목 정의·실명 표시 정책을 수정할 수 있는 기존 예외를 유지한다. 관리자 편집으로 다른 구성원의 필수 추가 값이 채워져도 그 구성원 계정 실명 관문까지 해제되는 것은 아니다. [core/common/middleware.py:38~50,93~105]

## 5. ‘요청할 정보 항목’을 이해시키는 편집안

첫 설명: **‘여기서는 구성원에게 받을 질문을 만듭니다. 저장하면 모든 구성원의 조직 설정 → 내 정보에 입력칸이 생깁니다. 구성원의 답은 구성원 목록에서 사람을 열어 확인·수정합니다.’** 항목 이름 입력은 질문 라벨이며 사람의 응답 값을 적는 칸이 아니라는 점을 명확히 한다.

| 관리자 입력 | 예시 | 구성원 내 정보에서 보이는 결과 |
|---|---|---|
| 항목 이름 | 근무 장소 | 입력 라벨 ‘근무 장소’ |
| 형식 | 선택지 | 단일 선택 드롭다운 |
| 선택지(한 줄에 하나) | 사무실 / 재택 / 혼합을 각각 다른 줄에 입력 | ‘고르기, 사무실, 재택, 혼합’ 옵션 |
| 필수 | 켬 | ‘근무 장소 (필수)’, 미입력 시 이 조직 사용 제한 |
| 도움말 | 주로 일하는 장소를 골라 주세요 | 입력 아래 도움말 |
| 순서 | 1 | 다른 질문보다 먼저 표시 |

‘항목 추가’를 누르면 예시 도움말을 가진 빈 편집 행을 만든다. 저장 전 실제 구성원 폼과 같은 모양의 **‘구성원이 보게 될 화면’** 미리보기를 바로 아래에 보여 준다. 미리보기에서 넣는 답은 테스트 값이며 저장하지 않는다고 표시한다. 저장 전에는 구성원에게 적용되지 않는다고 설명한다. 생성 예시 행을 실제 필수 질문으로 자동 저장하지 않는다.

형식 설명은 선택 즉시 보여 준다: 짧은 글은 한 줄 최대 200자(예: 직책), 긴 글은 여러 줄 최대 2,000자(예: 소개), 선택지는 한 항목만 선택·선택지당 최대 50자·최대 30개다. 항목은 최대 30개, 이름 최대 50자, 도움말 최대 200자다. 선택지가 아닌 형식에서는 선택지 편집 칸을 숨긴다. [core/orgs/member_info.py:24~26,50~75,85~87,145~151]

순서는 위·아래 이동 버튼으로 바꾸고 숫자·드래그에만 의존하지 않는다. 제목 변경은 같은 항목 ID의 기존 답을 유지한다. 삭제는 ‘구성원 화면과 관리자 열람에서 사라지며 다음 응답 저장 때 기존 값이 정리됩니다’라고 현재 동작을 정확히 안내한다. 삭제가 즉시 모든 저장값을 지운다고 표현하지 않는다. 선택지 제거·형식 변경 때는 영향을 받는 기존 응답 수를 안내하고, 검증에 맞지 않는 응답은 재입력 필요로 처리하는 정책을 제안한다. 현재 `missing()`은 비어 있는지만 검사하므로 **재입력 필요 상태·관문 검증 확장은 신규 구현 사항**이다. 필수 전환·선택지 변경 후 사용자에게 적용 전에 영향 요약을 보여 준다. 기존 민감정보 수집 제한 안내는 이 섹션에 유지한다. [core/orgs/member_info.py:6~7,124~129,148~151; settings.html:34]

## 6. 권한·URL·저장 범위·모바일

### 권한 경계

- 본인은 자신의 조직 한정 정보와 **본인 계정 실명**을 수정한다. 관리자는 **요청 URL의 조직에 속한 구성원의 조직 표시 이름·추가 정보 값**만 수정한다. 관리자 요청에 실명·계정 필드가 들어오면 거절한다. 멤버십 ID만으로 권한을 통과시키지 않고 조직·구성원·요청자 역할을 모두 확인한다.
- 다른 일반 구성원의 실명·추가 정보는 실명 표시 정책과 공개 이름을 제외하고 전달하지 않는다. 서버 주소·키는 일반 구성원 응답에 넣지 않는다. 키는 관리자에게도 평문 대신 설정 여부만 표시한다. [인벤토리 키 도움말; 현재 관리자 실명 열람: teams.html:21~23]
- 항목 정의·표시 정책·초대·역할 변경·구성원 제거·조직 설정 수정은 관리자 전용이다. `org.tags_by`에 따라 허용되는 본인 기술 태그 편집과 팀 자율 참여는 기존 일반 구성원 팀 화면에도 남긴다.
- 관리자 탭 요청은 서버에서 거절하며 HTML 숨김만으로 제한하지 않는다. 구성원에게 숨기는 탭과 관리자에만 보이는 자료는 전송하지 않는다. 업무 규칙 탭의 읽기 허용은 기존 읽기 전용 설정의 취지를 유지하는 선택이다.

### 제안 URL과 옛 주소 처리

| 주소 | 동작 |
|---|---|
| `/orgs/<id>/settings?tab=me` | 모든 구성원의 내 정보. `tab` 생략도 동일 |
| `?tab=members`, `rules`, `notifications`, `meeting`, `ai`, `integrations`, `organization` | 같은 설정 셸 내부 탭. `rules` 일반 구성원 읽기 허용, 나머지 관리자 전용 |
| `?tab=members&member=<membership-id>` | 해당 구성원 편집 패널을 복원·직접 링크. 조직 일치·관리자 권한 검사 |
| 옛 `/orgs/<id>/member-info` GET | 권한 확인 후 내 정보로 리다이렉트. 내부 안전한 복귀 주소만 유지 |
| 옛 `member-info` POST | 이전 클라이언트의 추가 정보 저장을 보존하는 호환 처리 후 내 정보로 303. GET 리다이렉트로 POST 본문을 버리지 않음 |
| 옛 설정 `#member-info` | 구성원 관리 / 요청할 정보 항목으로 연결되도록 옛 앵커 호환. 일반 구성원은 내 정보로 유도 |
| 옛 조직 GitHub·Discord GET | 관리자 확인 후 연동 탭의 해당 섹션으로 이동. OAuth 콜백·작업 POST 주소는 호환 유지 |
| 옛 전사 `?view=server` | 관리자 확인 후 회의·전사 / 전사 수단. 전사 작업·폴링·재시도 주소는 유지 |

쿼리는 제안이며 새 URL 구현은 이번 문서 작업 범위 밖이다. 관문의 `member_info.url()`·API 안내·`X-Blocked-Orgs` 링크도 새 내 정보 주소로 맞춰야 한다. 앵커는 서버에 전달되지 않으므로 기존 `#member-info` 호환은 클라이언트에서 인식하거나 셸에 안내 앵커를 남기는 방식이 필요하다. [core/orgs/member_info.py:186~208; common/middleware.py:70~82]

내 정보 폼, 관리자 정책 폼, 구성원별 정보 폼, 초대·역할·삭제 작업은 저장 범위를 구별한다. 관리자 정책은 **현재 탭의 변경 값·잠금만** 저장하고 다른 탭의 미전송 값을 초기화하지 않는다. 기존 구현이 조직 설정과 잠금을 일괄 교체하므로 부분 저장 서비스·원자성 검토가 필요하다. 구성원 관리의 이름 표시·항목 정의도 편집하지 않은 부분은 보존한다. 현재 한 정의 객체로 저장하는 구조를 분리된 화면 제목만으로 안전하다고 판단하지 않는다. 탭 이동 시 미저장 변경이 있으면 저장·버리기·계속 편집을 제공한다. 저장 후 섹션·스크롤 보존은 이미 수정된 요구 4를 유지한다. [core/web/views/orgs.py:599~614; core/orgs/member_info.py:96~112]

### 모바일과 디자인

기존 `.tabs`·입력·`.helptext`·설정 저장 막대·이력 컴포넌트와 디자인 토큰을 사용한다. 관리자 탭은 한 줄 가로 스크롤로 두고 현재 탭을 보이게 한다. 700px 이하 구성원 패널은 머리줄 아래 전체 시트, 닫을 때 해당 목록 행으로 초점을 돌린다. 개인정보 편집을 별도 페이지로 전환하지 않는다. [DESIGN.md:155~158,320~339]

좁은 화면에서는 항목 정의의 7열 표 대신 항목마다 라벨이 붙은 세로 편집 묶음을 쓴다. 카드 안 카드·항목마다 색면은 만들지 않으며 구분선으로 묶는다. 미리보기는 아래 접이식으로 배치한다. 저장 막대가 오류·마지막 입력·키보드를 가리지 않게 하고 터치 영역 44px·입력 글자 16px·읽을 수 있는 도움말 대비를 지킨다. [DESIGN.md:176~181,324,339,354]

## 7. 갈릴 지점과 선택 이유

| 지점 | 이 안의 선택 | 이유·구현 영향 |
|---|---|---|
| 실명 범위·관리자 권한 | 계정 공통 실명 유지, 관리자는 읽기 전용 | 정정된 추가 요구 5와 현재 모델 일치. legacy 열 재활성화·조직 실명 추가 없음 |
| 내 정보에서 계정 실명 편집 여부 | 본인은 같은 탭에서 편집 가능, 공통 범위 명시 | 요구 2의 별도 페이지 이동 없음과 요구 5의 관리자 편집 금지를 함께 충족 |
| 실명 표시 켬일 때 관리자 표시 이름 편집 | 본인과 동일하게 입력 숨김·서버 거절 | 표시되지 않는 이름을 관리자만 고쳐도 결과를 이해하기 어려움. 정책을 끄면 보존된 값 편집 가능 |
| 모든 탭 관리자 전용 vs 규칙 읽기 공통 | 내 정보 공통, 업무 규칙 읽기도 공통 | 기존 비관리자 읽기 기능과 ‘왜 업무가 막히는지’ 안내를 보존. 기밀 필드는 서버에서 제외 |
| 한도 설정의 위치 | 구성원 관리 / 참여·업무 배정 | 한 사람 기준 규칙. 업무 규칙 읽기에는 요약만 노출 |
| 전사 메뉴 전체 이동 | 서버·정책만 이동, 작업은 업무 메뉴 유지 | 실행 가능한 업무와 관리자 설정을 구분 |
| 변경 전후 개인정보 보관 | 기본안은 값 없이 변경 주체·항목·시각 기록 | 공용 이력에 개인 값을 복제하지 않음. 값 복구를 원하면 별도 접근·보존 정책 결정 필요 |
| 대리 수정 본인 통지 | 항상 기록, 전달 가능한 즉시 알림 + 내 정보 확인 전 안내 | DM 거부·미연결·가입 전 상태에서도 수정 사실이 남음. 통지 수단의 현재 지원 여부 조사 필요 |
| 탭 수 | 관리자 8개, 일반 구성원 2개 | 알림·회의·AI·연동을 한 ‘고급’ 탭에 몰아 다시 찾기 어렵게 만들지 않음. 모바일 스크롤 필요 |
| 저장 범위 | 탭별 정책 저장·구성원별 값 저장 | 현재 전역 폼을 여러 화면으로 나누면서 미전송 값이 소실되는 위험 예방 |

## 8. 범위와 확인 사항

분류안에는 인벤토리 84개와 정의 밖 관리 작업을 모두 매핑했다. 84개 key 자체는 변경하지 않는다. 구현 범위는 설정 셸·탭 이동, 구성원별 조직 정보 편집, 본인 실명 편집 UI·관문 경로 조정, 요청 항목 편집·미리보기, 부분 저장·권한 검사, 구성원 변경 이력·본인 통지, 옛 주소 호환이다. 실명 저장 모델·계정 공통 범위는 유지한다.

확인 불가: 실제 운영 데이터의 실명 공백·legacy 실명 분포, 개인정보 값 이력 보존에 관한 별도 운영 정책, 기존 개인 통지 수단의 정확한 재사용 가능 범위, 새 IA의 사용자 테스트 결과. 개인정보 응답값의 대리 수정·통지 범위는 구현 확정 전에 안내 문구와 보존 정책을 결정해야 한다. 이번에는 코드·커밋·운영 변경 없이 Sol 문서만 작성한다.
