# 조직 설정 IA 상호 검토 — Sol이 Claude 안을 검토

작성일: 2026-10-14. 코드 수정·커밋 없이 두 독립안의 통합 결정을 제안한다. 원본 두 안은 보존한다.

출처 약칭: **B** = `docs/drafts/org-settings-ia-brief.md`, **S** = `docs/drafts/org-settings-ia-sol.md`, **C** = `docs/drafts/org-settings-ia-claude.md`. 아래 `B:10` 같은 표기는 해당 파일의 줄번호다. 사용자 요구 번호는 B:9~12의 요구 1~4와 B:36~39의 정정된 요구 5를 뜻한다. 결정·권장은 검토자의 제안이며 현재 구현 사실과 구별한다.

## 1. 결론

Claude 안의 관리자/구성원 탭 묶음, ‘태스크·프로젝트’ 명칭과 상태 전환 중심 분류, 화면 내 본인 통지를 채택한다. 내 정보에서 **본인이 계정 공통 실명을 직접 수정**하는 Sol 안은 유지한다. 정정된 요구 5는 관리자의 계정 정보 수정을 금지하며 본인의 실명 편집을 금지하지 않는다. 조직별 실명 모델은 만들지 않는다. [B:10,36~39; S:185~187; C:25,33,201,228]

통합안은 **내 정보 / 구성원 관리 / 태스크·프로젝트 / 알림 / AI / 회의·전사 / GitHub / Discord / 조직 관리**의 9개 탭이다. 일반 구성원에게는 내 정보만 노출한다. 기존 업무 규칙 메뉴에서 공개 가능한 현재 적용 규칙을 읽도록 하되, 지금의 표가 전체 설정을 보여 준다는 전제는 바로잡는다. [S:15~24; C:30~39,266; core/orgs/settings.py:1313~1321]

## 3. 반대하는 점과 근거

### 3.1 실명을 읽기 전용 + 프로필 링크로 대체

- Claude는 본인도 프로필로 이동하게 하고 요구 2를 ‘고치는 길을 연결’로 재해석했다. 그러나 요구 2는 내 정보에서 실명·조직 표시 이름·추가 항목을 모두 설정하고 별도 페이지로 가지 않는다고 명시한다. 요구 5 정정은 **관리자** 수정 범위를 제한할 뿐이다. 계정 공통 저장 원본을 유지하면서 본인 실명 입력을 같은 탭에 두면 두 요구를 함께 만족한다. [C:13,144,214~217,228,292; B:10,36~38]
- 따라서 본인은 ‘실명(계정 공통)’을 직접 수정하고 다른 조직에도 반영됨을 명시한다. 관리자 패널은 같은 값을 읽기만 한다. 로그인 ID·계정 표시 이름·비밀번호의 편집은 계정 설정에 남긴다. [S:185~187,202,231; core/accounts/models.py:14~17]

### 3.2 두 관문을 한 관문처럼 설명

- ‘관리자가 필수를 다 채우면 조직을 쓸 수 있다’는 안내는 계정 실명 미입력일 때 성립하지 않는다. 현재 미들웨어는 계정 실명부터 검사하며 조직 내 정보는 계정 실명 관문의 예외가 아니다. `member_info.url()` 변경만으로 본인 실명 미입력 흐름이 해결되지 않는다. [C:198,230,280,307; core/common/middleware.py:38~51,93~105; 요구 2·5]
- 통합안은 내 정보 GET·본인 저장에 제한된 계정 실명 관문 예외를 추가하고, 관리자 탭 우회는 허용하지 않는다. 계정 실명이 채워진 관리자에게 자신의 조직 필수 정보 미완료 상태에서 항목 정의·표시 정책을 고칠 예외는 유지한다. 관문 해제 안내는 두 조건을 확인해 ‘조직 필수 정보 입력 완료’와 ‘조직 사용 가능’을 구별한다. [S:206; B:10,38~39]
- Claude의 ‘관문이면 내 정보만 활성’과 ‘관리자는 조직 관리 탭도 열림’은 권한 표·본문에서 다르게 적혔다. 위 조건부 예외를 권한표에 명시해야 한다. [C:230,262~264]

### 3.3 폼 하나 원칙과 이름 표시 독립 폼의 충돌

- 개요는 탭마다 폼 하나·저장 하나지만 구성원 관리 이름 표시 방식은 다른 저장 버튼으로 정의한다. 초대·역할·제거까지 한 폼에 묶을 수 없다. [C:41,146,193~195,251; B:9,29,39]
- 정책 저장, 구성원 한 명의 값 저장, 초대·역할·제거는 별도 저장 범위로 확정한다. 표시 정책과 항목 정의도 독립 폼으로 하되 각각 같은 `member_fields` 객체의 상대 값을 보존한다. 탭별 정책 저장은 다른 탭의 값·잠금을 보존해야 한다. 현재 일괄 교체 구현을 재사용하는 것만으로는 충족되지 않는다. [S:251; core/orgs/member_info.py:96~112; core/web/views/orgs.py:599~614; 요구 1·4·5]

### 3.4 이력의 대상 식별·구현 규모 설명이 부족

- Claude가 제안한 `target_type="org"`, `field="member_info"`만으로는 어떤 구성원의 변경인지 식별할 수 없다. 현재 ChangeLog에는 조직 target_id와 일반 필드·전후 값·note 등이 있지만 멤버십 전용 FK가 없다. ‘그 구성원 행 기준으로 읽기’를 구현하려면 구조화된 대상 식별과 조회 권한을 정해야 한다. [C:200~201,307; core/tasks/models.py:446~467; 요구 5]
- 사용자 실명·추가 정보 값은 이력 문자열에 남기지 않는다. 표시 이름 이력은 기존 이력이 있다는 사실과 신규 본인 통지 목적을 구별한다. 통합안의 신규 구성원 정보 이력은 표시 이름도 값 대신 항목명으로 기록하고, 기존 nickname 이력은 기존 접근 범위를 유지한다. ‘모델 변경 없음’은 미확정이며 필요한 대상 식별·확인 시점 저장 구조를 구현 단계에서 결정한다. [C:200,302,307; S:177~179,269; B:39]

### 3.5 업무 규칙 읽기 대체의 전제가 불완전

- 업무 규칙 메뉴가 있으므로 별도 공통 규칙 탭을 없애자는 IA에는 동의한다. 다만 현재 `enforced()`는 기본값과 같은 항목을 제외하므로 모든 적용 규칙을 대체해서 보여 주는 화면은 아니다. scope·hidden 검사만으로 순회하므로 구성원 공개 가능 항목도 별도로 선별해야 한다. [C:266,294; core/web/views/orgs.py:468; core/orgs/settings.py:1313~1333; B:26~27]
- 통합 시 업무 규칙의 공개 규칙 요약을 기본값 포함 허용 목록으로 보완하고 서버 주소·키·구성원 상세 값은 제외한다. 본인 내 정보에서는 해당 업무 규칙 메뉴로 연결한다. 이는 사용자 요구의 명시 의무라기보다 기존 읽기 기능을 줄이지 않기 위한 조건이다. [S:24,232; core/web/views/orgs.py:594]

### 3.6 링크 호환·디자인·공개 이름 설명 정정

- 옛 member-info를 전부 301로 보내면 기존 POST 저장 처리가 빠진다. GET은 권한 확인 후 리다이렉트하고 POST는 호환 저장 후 303으로 보내는 Sol 방식을 채택한다. member-fields POST는 초기 전환기에 서버 호환 처리하고, 클라이언트에 307 재제출만 맡기지 않는다. [C:273~274; S:243~249; 요구 2·4]
- 항목마다 중첩 카드가 생기는 방식과 220px 사이드바를 고정 확정하지 않는다. 질문별 라벨·구분선·미리보기 구조는 채택하되 기존 컴포넌트와 패널 토큰을 따른다. 패널을 URL로 복원하더라도 목록을 밀거나 목록 화면 밖으로 이동시키지 않는다. [C:187,240,284; S:255~257; DESIGN.md:153~157,176~180,354; 요구 1·2·4]
- ‘남의 실명 문자열이 구성원 응답에 없어야 한다’는 문장은 실명 표시 끔 조건을 붙여야 한다. 켬일 때 실명은 공개 표시 이름으로 쓰인다. 별도 계정 실명 상세 필드는 일반 구성원에게 제공하지 않는다. [C:16,267; core/orgs/names.py:34~42; B:11,39]

## 5. 합칠 때의 최종 제안

### 5.1 탭 목록·섹션 순서

아래 순서와 명칭을 통합안으로 제안한다. 관리자 영역은 관리자에게만 전송한다. [B:26,31; C:25~39; S:15~22]

| 탭 | 권한 | 섹션 순서 |
|---|---|---|
| 1. 내 정보 | 모든 구성원, 본인 편집 | 실제 표시 이름 미리보기 → 실명(계정 공통)·조건부 조직 표시 이름 → 조직이 요청한 정보 → 관리자 수정 기록·확인 안내 → 업무 규칙·개인 설정 링크 |
| 2. 구성원 관리 | 관리자 | 구성원 목록·패널 → 가입 전 구성원 → 초대 링크·초대 정책 → 이름 표시 방식 → 요청할 정보 항목·미리보기 → 팀·기술 태그 정책 |
| 3. 태스크·프로젝트 | 관리자 | 생성 기본값 → 진행·검토 → 변경 사유 → 기한 → 프로젝트 권한 → 프로젝트 기본값 |
| 4. 알림 | 관리자 | 기한 알림 → 막힘·검토 알림 → 주간 보고 → 채널 게시 → GitHub 알림 |

### 5.4 합칠 때 남길 구현 확인 사항

- **확인 필요**: 멤버십별 변경 이력 식별·조회 권한·확인 시점·가입 전 인계 방식. 현재 ChangeLog 필드만으로 대상 식별이 완성됐다고 판단하지 않는다. [core/tasks/models.py:446~467; C:200~201]
- **확인 필요**: 공개 규칙 허용 목록·기본값 포함 표시 범위·숨김 및 비밀 값 제외. 기존 `enforced()`를 그대로 전체 조회 대체로 쓰지 않는다. [core/orgs/settings.py:1313~1333]
- **신규 구현 범위**: 본인 실명 편집·계정 관문 예외, 관리자 값 편집·검증 분기, 부분 저장·잠금 보존, 항목 정의 영향 계산·미리보기, 이력·앱 내 통지, 옛 POST 호환. 선택지·형식 변경에 따른 기존 값의 재입력 필요 판정은 현재 `missing()`에 없으므로 별도로 명시한다. [S:202~206,225,251; core/orgs/member_info.py:124~129,139~157]
- **확인 불가**: 실제 운영 데이터의 영향 인원·사용자 테스트 결과·추가 이력 보존 정책. 이번 검토에서 동작 검증이나 운영 변경은 하지 않았다. [S:278]

이 문서는 상호 검토 결과이며 최종 구현 승인 문서는 아니다. 통합 담당자는 위 차이별 결정을 최종안에 반영하고, 본인 실명 편집에 관한 양안의 이견을 최종 보고에 남긴다.
