# Discord 관리 확장 및 연동 도움말 제안

2026-10-04. 기존 TASK-41 배포 이후 추가 요청. 이 문서는 이전 인계 문서를 보존하는 별도 기록이다.

## Discord 웹 관리 제안

조직의 Discord 화면에 서버 상태와 프로젝트별 채널 연결 관리표를 둔다. 프로젝트 설정에서는 해당 프로젝트 행으로 이동한다. 각 작업은 조직 관리자 여부와 봇의 Discord 권한을 따로 설명한다.

| 우선순위 | 기능 | 사용자 결과 | 구현 범위 |
|---|---|---|---|
| MVP 1 | 서버·채널 현황 및 새로고침 | 카테고리, 텍스트 채널, 프로젝트 연결을 한눈에 확인 | 기존 채널 조회 제어 API 활용 |
| MVP 2 | 기존 채널 연결·변경 | 이름과 카테고리로 선택 후 프로젝트 연결 | 기존 assign 활용, 동일 서버 검증 |
| MVP 3 | 프로젝트 연결 해제 | PM 연결만 해제하고 Discord 채널 유지 | 기존 assign 활용, 해제 범위 확인 문구 |
| MVP 4 | 새 프로젝트 채널 생성 | 이름·카테고리 선택 후 생성과 연결 | 기존 생성 API 활용, 생성 성공/연결 저장 실패 구분 |
| MVP 5 | 연결 후보 미리보기 | 기존 연결 유지, 동명·복수 후보·신규 생성 제안을 확인 후 개별 적용 | MCP 계획 로직 공통화 또는 웹 계획 API 필요 |
| 후속 | 조직 알림 채널 선택 | 웹에서 알림 수신처 변경 | 세션 사용자용 저장 경로 추가 |
| 후속 | 팀별 채널 연결·생성 | 팀 대화방을 웹에서 준비 | Discord slash 구현을 웹 제어 API로 확장 |

근거: `discord_service/discord_service/control.py:19-159`, `mcp_server/mcp_server/server.py:116-172`, `core/api/routers/discord.py:220-225`, `discord_service/discord_service/slash.py:327-334`.

선행 설계: 브라우저가 내부 Bearer 토큰을 받지 않도록 웹 서버가 제어 서비스를 호출한다. Discord 봇 토큰은 기존 봇 서비스에 유지한다. PM 조직 관리자와 Discord 채널 관리자의 권한 차이를 명시한다. 삭제·권한 일괄 변경은 첫 범위에 포함하지 않는다. 실제 봇 권한과 운영 채널 작업은 이번 조사에서 확인하지 않았다.

## 이번에 반영한 화면 개선

- 조직·프로젝트의 태스크 가져오기 이슈 화면: 본문을 기존 안전한 DOM Markdown 렌더러로 표시하고 원문 보기 제공. 체크리스트는 읽기 전용. 제목·목록·강조·인용·코드·링크 등 기존 지원 문법을 사용하며 GitHub Markdown의 표 등 모든 문법을 구현한 것은 아니다.
- GitHub 접근 팀: 성공한 빈 목록과 실패를 구분. 실패 시 설치 정보 없음 / HTTP 상태 / 네트워크 오류를 보존하고 원인을 단정하지 않는다. 목록은 페이지네이션으로 조회한다.
- 같은 화면에 해결 절차, 공식 문서, 질문 프롬프트 복사, 선택·복사 가능한 원문을 제공한다. 질문에는 저장소명과 조회 상태를 포함하고 API 오류 원문·토큰·개인키를 넣지 않는다.
- 저장소 접근 불가: 캐시된 계정 목록에 없는 상태임을 설명하고 프로필에서 접근 목록을 다시 확인하도록 안내한다.

접근 팀 API에는 저장소 **Administration: Read-only**가 필요하다. 조직 Members 읽기와 다르며 쓰기 권한은 필요하지 않다. 기존 `docs/GUIDE-V2-07-github-read.md:16-34`는 Administration을 요청하지 않는 설정이다. 설치의 실제 권한을 이번에 조회하지 않았으므로 사용자의 오류가 권한 때문이라고 확정하지 않는다. 권한을 유지할 때는 GitHub에서 직접 확인하고, 추가할 때는 앱 관리자 변경 및 설치 관리자 승인 후 다시 조회한다.

공식 근거: [List repository teams](https://docs.github.com/en/rest/repos/repos#list-repository-teams), [앱 권한 변경과 설치 승인](https://docs.github.com/en/apps/maintaining-github-apps/modifying-a-github-app-registration#changing-the-permissions-of-a-github-app).

## 다른 화면에서 필요한 안내

공통 패턴은 **확인된 상태 → 사용자가 할 일 → 관리자가 할 일 → 해결 절차 → 질문 복사**로 제안한다. HTTP 상태만으로 권한 문제를 확정하지 않고 부분 성공은 따로 표시한다.

| 우선순위 | 현재 문제 | 추가할 설명·행동 | 코드 근거 |
|---|---|---|---|
| 높음 | OAuth 연결 실패가 한 문구로 합쳐짐 | 연결 재시도, 운영자의 콜백 설정 확인, 오류 단계·시각 포함 질문. code/state 제외 | `core/web/views/github.py:114-122` |
| 높음 | 연결 성공 후 저장소 초기 조회 실패를 숨김 | 계정 연결 성공과 목록 조회 실패 분리, 목록 다시 확인 | `core/web/views/github.py:127-133` |
| 높음 | 저장소 후보 없음이 앱 미설치/API 실패/정상 빈 목록을 합침 | 설치 상태·조회 상태 구분, 조직 관리자 확인 | `core/github/services.py:197-212` |
| 높음 | 이슈 동기화 실패의 해결 경로 부족 | 재시도, 마지막 성공 시각, 설치·읽기 권한·네트워크 점검과 질문 복사 | `core/github/services.py:745-760` |
| 높음 | PM만 변경되고 GitHub 반영 실패 시 재시도 경로 없음 | 적용된 항목·실패 항목 분리, PM 작업 반복 방지, GitHub 반영만 재시도 설계 | `core/github/writes.py:47-58` |

위 표는 후속 개선 제안이며 이번 변경에서 모두 구현한 것은 아니다. 조사 근거의 줄번호는 변경 전 기준이다.

## 검증

GitHub 테스트 전체 126개, Ruff, Django check 통과. 조직·프로젝트 이슈 본문 escaping, 읽기 전용 표시, 빈 팀 목록과 실패 구분, HTTP 상태 보존을 검증했다. 독립 코드 검토에서 중대 오류 없음.

Astra는 Django 테스트로 렌더한 로컬 HTML 4개를 390/1280px 두 폭에서 검증했다. Markdown 제목·강조·코드, 비활성 체크리스트, 원문 보기, 스크립트 비실행, 페이지 가로 넘침·pageerror 없음, 질문 실제 클립보드 복사 4/4 일치를 확인했다. 클립보드 거절 모의 시 수동 복사 창과 읽기 전용 원문 대체도 확인했다. 프롬프트 입력창의 높이가 좁다는 피드백을 반영해 최소 140px로 조정했다. 증거는 `%TEMP%/integration-review-20261004`의 렌더본 및 Astra 별도 검증 자료다.

이 검증은 로컬 렌더본 검증이다. GitHub 실제 설치 권한, Discord 생성·연결, 운영 사용자 로그인 흐름은 이번 범위에서 검증하지 않았다. 변경은 UI-UX 브랜치 작업 파일에 있으며 아직 운영에 배포하지 않았다.
